# 测试规范

测试分两层，**归属看"谁定义、谁判定"，不看"谁敲的代码"**。

## 1. 用例归属

| | 开发自测 | QA 测试 |
|---|---|---|
| 验证什么 | 代码按 Plan 的设计工作 | 系统符合需求规格 |
| 谁定义 / 判定 | 开发本人 | **QA** |
| 编号 | 无编号，命名表达意图 | `TC-xxx`，与文本用例一一对应 |
| 存放位置 | 源码旁 | 文本 `{{TEST_CASES_DIR}}/`，自动化 `{{E2E_DIR}}/tests/qa/` |
| 合并闸门 | 否 | **是** |
| 失败意味着 | 代码写错了 | 需求没实现 / 理解有偏差 / 规格有歧义 |

- QA 用例的自动化实现可以由开发代写，但**定义权与判定权归 QA**
- 开发自测全绿 ≠ 需求被实现，不能替代 QA 测试
- 先有文本用例，再写自动化；反过来做会漏场景

## 2. 开发自测

### 2.1 分层策略

| 层 | 测试类型 | 关注点 |
|---|---|---|
| adapter | 集成 / 接口测试 | 路由、参数校验、状态码、鉴权、错误体 |
| application | 单元测试 | 用例编排、事务边界、分支覆盖 |
| domain | 单元测试 | 业务不变量、状态守卫、边界值 |
| infrastructure | 集成测试 | 仓储实现、SQL / 映射、外部调用契约 |
| 前端组件 / composable | 单元测试 | 渲染、交互、组合逻辑分支 |
| 端到端 | 自测 E2E | 关键链路打通，放 `{{E2E_DIR}}/tests/dev/` |

### 2.2 覆盖要求

- 每个对外 API **必须** 有测试：1 个 Happy Path + 关键失败分支（参数错误 / 权限不足 / 业务冲突）
- 每条业务规则至少 1 条 domain 测试
- 新增分支未覆盖，不进入代码评审

### 2.3 命名

- 类名 `{被测对象}Test`；方法名 `should_{action}_{expected}`
- 用例名说明 **业务行为**，不写实现细节
- 不写 `TC-` 编号（那是 QA 用例的）

## 3. QA 测试

- 需求规格的每条验收标准、每条业务规则 → 至少 1 条 `TC-xxx`
- 文本与自动化共用同一编号，一一对应
- 四类产物：
  - E2E 验收文本 `{{E2E_CASES_DIR}}/`
  - E2E 自动化 `{{E2E_DIR}}/tests/qa/`
  - 手动用例 `{{MANUAL_CASES_DIR}}/`
  - 冒烟用例 `{{SMOKING_CASES_DIR}}/`
- 用例可独立重复执行，不依赖执行顺序

## 6. 失败处理

- 自测失败：定位根因后修，不用重跑掩盖
- QA 验收失败：先判断是"代码错"还是"规格歧义"，后者回 `{{FEATURES_DIR}}/` 改规格并同步 QA 用例
- 偶发失败（flaky）：必须定位根因；不允许标记跳过长期存在
