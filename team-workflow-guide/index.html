1. 项目准备

目标：项目「可被 harness 管理」——规范、目录、工具齐。

协作口诀：TL 装机与定规矩，QA 定闸门，BA 定方向。规矩未定不进迭代。

1.1 谁做什么

步骤主责产物
初始化 AGENTS.md + docs/TLAGENTS.md、docs/**
安装 SDD skillTL.agent/skills/
安装 MCPTL.mcp.json / opencode.jsonc
定架构与标准TLdocs/standards/、docs/facts/
定测试闸门QA + TLtest:qa 进 CI
业务目标与首迭范围BA / PM迭代目标一页纸

1.2 接入顺序

全部交给 AI Agent 按 skill 执行，人只确认目标项目路径与关键决策。顺序不能变：

  1. 铺 harness — 对 Agent 说：用 harness-installer 给目标项目初始化 AGENTS.md 与 docs/ 骨架。
    完成后由 TL 补全 AGENTS.md 里的业务 / 架构 TODO（Agent 可起草，人必须拍板）。
  2. 装 SDD skills — 对 Agent 说：用 agile-team-sdd 把 16 个流程 skill 安装到目标项目的 .agent/skills/。
  3. 装 MCP 工具链 — 对 Agent 说：用 tool-chain-installer 把 MCP 配置写入项目（如 .mcp.json / opencode.jsonc）。
  4. （可选）装 overnight-runner — 需要夜跑 Plan 时，再让 Agent 安装并写好队列配置。
装完 skill / MCP 后必须重启 opencode（或等价 IDE Agent），配置才生效。不要跳步：先有 AGENTS.md 与 docs/，再装 skills，路径才指向真实目录。

1.3 出口条件

  • AGENTS.md 关键 TODO 已填
  • skill + MCP 可用
  • 文档树与测试归属约定写清
  • 团队对齐三条铁律（规范先于代码 / 测试先于实现 / 文档同批次）

2. 迭代前方案设计

目标：进开发前，业务与技术都「可测、可估、可确认」。

2.1 流水线

BA 拷问 → 规格 + 原型图 ba-grill-me · ba-write-spec
PM 估算与排期 pm-estimate
规格确认后并行
TL · ★ 高阶技术方案 TRD 人工确认
∥
QA 文本用例 TC qa-write-cases
出口 两边就绪 → 进入迭代中 DEV 再写 Plan

规格与原型落在 docs/features/iteration[n]/。TRD 未确认不得进入迭代中写 Plan；QA 文本用例未齐不得声称有验收基线。

2.2 交接

从 → 到交出什么
BA → TL / QA / DEViteration[n]/*.md 规格 + 原型图 + 范围边界 + AC/R
TL → DEV已确认 TRD（技术边界与取舍）
QA → DEVTC 映射表（自动化可代写）

2.3 可进入迭代中 DoR

  • 本迭规格已确认（docs/features/iteration[n]/*.md，R / AC 齐）
  • 本迭原型图已输出（docs/features/iteration[n]/prototypes/）
  • TRD 已人工确认
  • 本迭 TC 文本用例齐，且映射到 AC/R

3. 迭代中开发

目标：DEV 先写 Plan（对照 TRD），确认后再实现；经自测与 QA 验收后合并、可发布；复盘回写 harness。

3.1 流水线

DEV（+ AI）
★ 写 Plan dev-plan
循环
实现 + 自测 dev-build 写码 ↔ 跑测
↻ 未通过则继续
评审 UI / 代码 / 事实文档 review · ba-gen-facts
QA · ★ 合并闸门 E2E + 文本勾选 qa-run-e2e
DEV 开 MR dev-create-mr
TL 上线清单 dev-release-plan
PM 复盘回写 pm-retro
Plan 未确认不得写实现。overnight-runner 只跑已确认的 Plan；不做 Plan / TRD 闸门本身。

3.2 并行边界

  • 多 DEV 可并行，契约以已确认 Plan + api.yaml 为准（并服从 TRD 边界）
  • QA 自动化可由 DEV 代写，勾选与放行权在 QA
  • 自测绿 ≠ 可合；QA 过 ≠ 可忽略自测红
  • 规格外行为 = 缺陷（除非 BA 认可）

3.3 Definition of Done

  • Plan 已确认且按 Plan 实现
  • 每条 AC / R 都有对应 QA 用例且通过；文本用例勾选完毕
  • 开发自测全绿；关键 API 覆盖 Happy Path + 失败分支
  • 事实文档已更新；无遗留 TODO / 调试代码
  • 上线清单完成（TL）；复盘改进已回写 harness（PM）

4. 测试分层与归属

开发自测对「我写的代码」负责；QA 测试对「需求有没有被实现」负责。

维度开发自测QA 测试
验证什么代码按 Plan 工作系统符合需求规格
判定人开发本人QA
编号无TC-xxx
位置源码旁、e2e/tests/dev/docs/、e2e/tests/qa/
合并闸门否是

编号映射：每条 R-xxx、AC-xxx 至少对应一条 TC-xxx。

5. 角色手册（速查）

BA · 业务分析

让开发不需要猜就能开始做。规格写「做什么」，不写表名/SQL；同步输出 HTML 原型图。本迭产物放在 docs/features/iteration[n]/。

ba-grill-meba-write-spec

PM · 项目经理

估算有据；复盘必须落到可验证的 harness 文件改动。

pm-estimatepm-retro

TL · 技术负责人

装机定规；迭代前写高阶技术方案（TRD）并确认；迭代中做代码评审与发布清单。工具链与密钥不落盘也归 TL。

dev-code-reviewba-gen-factsdev-release-plan

DEV · 开发

迭代中先写 Plan（对照 TRD / 规格），确认后再实现与自测。复用现有模式，不自创；自测不写 TC 编号。

dev-plandev-builddev-ui-reviewdev-debug

QA · 测试

定义与判定权归 QA。先文本用例，再自动化；不过不能合。

qa-write-casesqa-run-e2eqa-write-manual-plan

AI Agent

可靠执行者，不是打字机。需求/规范有歧义 → 停下来问。不把「自测全绿」写成「需求已满足」。
