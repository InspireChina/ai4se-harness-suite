1. 项目准备

目标：项目「可被 harness 管理」——规范、目录、工具齐；高阶架构意图落盘。

协作口诀：TL 装机与定规矩，BA 先落业务意图、TL 再接技术架构，QA 定闸门，BA/PM 定方向。规矩与架构未定不进迭代。

1.2 接入顺序

全部交给 AI Agent 按 skill 执行，人只确认目标项目路径与关键决策。顺序不能变：

  1. 铺 harness — 对 Agent 说：用 harness-installer 给目标项目初始化 AGENTS.md 与 docs/ 骨架。
    完成后由 TL 补全 AGENTS.md 里的业务 / 架构 TODO（Agent 可起草，人必须拍板）。
    多仓库项目先定布局（见 §7）—— 布局决定 AGENTS.md 与文档里写哪些路径。
  2. 装 SDD skills — 对 Agent 说：用 agile-team-sdd 把 27 个流程 skill 安装到目标项目的 .agents/skills/。
  3. 装 MCP 工具链 — 对 Agent 说：用 tool-chain-installer 把 MCP 配置写入项目（如 .mcp.json / opencode.jsonc）。
  4. （可选）装 overnight-runner — 需要夜跑 Plan 时，再让 Agent 安装并写好队列配置。
  5. 业务架构意图 — 对 Agent 说：用 ba-arch-plan 起草 docs/architecture/business/（产品边界、术语基线、核心聚合、迭代规划），并给出「核心聚合 → 建议容器」交接表。
  6. 技术架构 — 对 Agent 说：用 tl-arch-plan 接上一步，填 docs/architecture/tech/（C4 上下文/容器、跨迭代 ADR）；容器要能承载上一步的核心聚合。两步都完成，architecture 才算可读。
装完 skill / MCP 后必须重启 opencode（或等价 IDE Agent），配置才生效。不要跳步：先有 AGENTS.md 与 docs/，再装 skills，路径才指向真实目录。

1.3 出口条件

  • AGENTS.md 关键 TODO 已填
  • skill + MCP 可用
  • 文档树与测试归属约定写清
  • 仓库布局已定：组件在 containers/ 下就位（单仓 / 嵌套 / 并列三者之一，见 §7）
  • docs/architecture/ 已有可读的：业务侧（product 边界 / 术语 / 核心聚合 / 首迭规划）+ 技术侧（C4 / ADR）（可与装机并行，但进迭代前须齐）
  • 团队对齐三条铁律（规范先于代码 / 测试先于实现 / 文档同批次）

4. 测试策略与归属

目标：九层测试各有人管、各有落点、各有闸门 —— 少一层，缺陷就往下一层漏。

AI 写的用例便宜，但「不可信」才是默认状态。所以策略里既有「谁写」，也有「用例本身怎么被验证」—— 后者靠 4.2 的变异测试。

4.2 变异测试：验证用例「有没有牙」

AI 可以写出很像样的 E2E，却只断言「页面上有个数字」—— 实现改坏了它照样绿。 用例存在 ≠ 用例能证伪，这是 AI 测试的默认风险，也是它需要单独一层防护的原因。

  • 怎么做：往被测代码里注入小改动（改比较符、删一行校验、反转条件），再跑 E2E。 用例必须变红；没变红就说明这条用例抓不住这个缺陷
  • 判据：有效变异杀光（或达到项目约定阈值），E2E 才算可信； 不许登记成「已知债务」放行 —— 缺口不是债务
  • 别误用：环境不稳、数据没隔离会造成假「没杀死」，先排除不稳定再下结论
变异测试失败 → 回研发自测，而不是把断言改一改了事。 失败的含义是「用例太弱，也就是自测那一步没做扎实」：回 dev-self-test / dev-ui-review 重跑， 把断言补到能证伪，再从第 ② / ③ 步回到 E2E —— 不让弱用例带着「全绿」进合并。

4.3 归属判定

归属看谁定义、谁判定，不看谁敲的代码：开发自测对「我写的代码」负责； QA 测试对「需求有没有被实现」负责。

7. 仓库布局：单仓 / 嵌套 / 并列

目标：harness 与业务代码怎么放，一开始就定下来 —— 装机时的目标路径、文档里的链接、CI 的 checkout 都依赖它。

默认选方式二（嵌套）：主仓库装 harness，业务组件以 submodule 挂在 containers/<组件>。只有当「组件少、没人管权限」或「harness 要给多个产品复用」时才偏离。

7.1 先选一种

你的情况选一句话理由
一个产品，前后端 + 文档都是同一拨人方式一 · 单仓路径最简单，没有指针要维护
业务代码已有独立仓库 / 要按组件切权限与发布方式二 · 嵌套（推荐）目录路径与单仓完全一致，skill 与占位符零改动
harness 是平台团队交付物，要服务 N 个产品方式三 · 并列解耦彻底，代价是 CI 与文档链接都要跨仓

7.2 三种形态对比

维度一 · 单仓二 · 嵌套（推荐）三 · 并列
目录长相一个仓全装下主仓 + containers/* 子模块两个平级仓库，靠 ../ 关联
harness 在哪同仓主仓（与 docs/ 同级）独立仓

主要代价仓库膨胀、CI 全量指针要跟着子仓提交走跨仓路径与链接极易断

7.3 方式一 · 单仓（mono repo）

my-product/
├── AGENTS.md        .agents/skills/        .mcp.json
├── docs/             architecture · features · facts · standards
├── containers/       backend/  frontend/      ← 就是普通目录
└── e2e/
  • 何时选：单产品、组件 1–3 个、团队规模小；新项目起步的默认选择
  • example-project/ 就是这个形态 —— 先按它长起来，撑不住再拆
  • 坑：仓库变大后 clone 慢、CI 每次全量、没法「后端仓只给后端同学写权限」
  • 何时该拆：单目录超过 ~2GB，或 CI 全量已超过 15 分钟

7.4 方式二 · 嵌套仓库（推荐）

my-product/                    ← 主仓库：harness + 文档 + 胶水
├── AGENTS.md
├── .agents/skills/            ← 27 个 skill（随主仓分发）
├── docs/                      ← architecture / features / facts / standards
├── containers/
│   ├── backend/               ← submodule → git@…/svc-backend.git
│   └── frontend/              ← submodule → git@…/web-app.git
└── e2e/

为什么推荐：containers/backend 与单仓里的普通目录路径完全一样， 所以 AGENTS.md、27 个 skill、占位符（BACKEND_DIR / FRONTEND_DIR）、 测试命令（cd containers/backend && mvn test）一个字都不用改； init-harness.sh 的目录探测本来就优先 containers/backend|frontend。 权限与发布仍按子仓库走，而 agent 只要打开主仓一个工作区。

# 主仓里挂子仓（子仓必须已有远端仓库）
git submodule add git@github.com:org/svc-backend.git containers/backend
git submodule add git@github.com:org/web-app.git  containers/frontend

# 新人 clone（漏了 --recursive 就补这一步）
git clone --recurse-submodules git@github.com:org/my-product.git
git submodule update --init --recursive

五条铁律：

  1. 先子仓、后主仓：代码改动必须先在 containers/backend 里 commit + push， 再回主仓 commit 那个指针。反了就等于「主仓指向一个没有你代码的 commit」
  2. 指针钉 commit，不钉分支：要跟分支就显式 git submodule update --remote，并且知道 CI 会跟着漂
  3. 文档只留主仓：docs/features/、docs/architecture/ 不进子仓库 —— 否则同一份规格两处版本
  4. 构建产物各自 ignore：containers/*/target、node_modules、dist 在各自仓里管
  5. 子仓可见性：看不到子仓的人等于看不到代码；至少要读权限，CI 用机器账号拉

7.5 方式三 · 独立 harness 仓库（并列）

workspace/
├── harness/     ← 上下文 + skills + 文档骨架（独立仓库，平台团队维护）
└── product/     ← 业务代码（独立仓库）
  • 关联靠相对位置：../harness、../product
  • 装进 product 的产物必须用 PATH_MODE=relative —— 绝对路径会把安装机的主目录写进 skill
  • 适合：多个产品共用一套流程、harness 有独立发版节奏、harness 仓允许只读
  • 坑：CI 要 checkout 两次（actions/checkout 的 path: 参数）、 跨仓相对链接一改就断、MR 里看不到「流程改动 + 代码改动」的完整 diff
最大的坑是 agent 的工作区边界：IDE Agent 通常只认打开的那个目录， ../harness/docs/… 多半读不到。现实中只有两种用法 —— 人切换目录（装机时站在 product，查架构文档时切到 harness）， 或者把 harness 用符号链接 / submodule 挂进 product（这时其实已经退化成方式二）。

7.6 三种形态下怎么升级 harness

形态升级动作注意
单仓直接在仓里跑三个安装器与业务改动在同一个 MR，容易一起评审
嵌套在主仓跑三个安装器不要在 containers/* 里跑 —— 子仓里的 skill 副本是无效副本
并列在 harness 仓改，再 PATH_MODE=relative 装进 product装完要提交 product 里的 .agents/ 与 docs/

7.7 反模式

  • 把 harness 复制进多个仓各自改 → 立刻漂移，同一套 skill 各有各的版本
  • 跨仓用绝对路径（/Users/…、/home/…）引用 harness → 换机器即断
  • submodule 指向个人分支 → 别人拉不到
  • 子仓 A 里再挂子仓 B，深度超过两层 → 指针地狱，没人敢升级
