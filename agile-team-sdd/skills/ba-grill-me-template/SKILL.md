# BA：拷问需求

需求写不清楚，是后面所有返工的根源。这个 skill 的唯一目的：**在动手写规格之前，把歧义问干净**。

## 什么时候用

- 需求只有一两句话，没有明确验收标准
- 同一句话有 **两种以上** 合理解释
- 需求里出现"支持"、"优化"、"友好"、"快速" 这类不可测的词
- 涉及 **权限、状态流转、数据迁移、金额/库存** 等高风险面

**已经澄清过的不用再问一遍。** 先读 `{{FEATURES_DIR}}/` 里已有的规格和 `{{DESIGNS_DIR}}/` 里的事实文档。

## 拷问协议

### 一次问 3~5 个，不要一次甩 30 个

一次给太多问题，对方会随便答，答案质量会塌。分批问，每批之后确认理解一致。

### 按主题推进，一个主题问透

推荐顺序：

1. **业务目的** —— 这件事做完，谁的什么问题被解决了？
2. **角色与权限** —— 谁能看到、谁能改、谁不能碰？
3. **数据与字段** —— 有哪些字段？谁填？校验规则？默认值？
4. **流程与状态** —— 有状态流转吗？谁能触发？非法流转怎么办？
5. **异常与边界** —— 重复提交、超时、并发、数据不存在？
6. **验收标准** —— 怎么算做完了？

### 只问"代码里查不到"的

能自己查到的别问：

| 问题 | 先查 |
|---|---|
| 现有接口长什么样 | `{{API_SPEC}}`、Controller |
| 表结构 | `{{DB_SCHEMA_DOC}}`、迁移脚本 |
| 领域模型 | `{{DOMAIN_MODEL_DOC}}`、聚合类 |
| 已有业务规则 | `{{BUSINESS_RULES_DOC}}` |
| 现有枚举取值 | `{{DATA_DICT_DOC}}` |

查完再问，问的是 **产品决策**，不是事实。

### 阻塞性问题必须问到答案

下面这些没答案就不能往下走，必须停下来问：

- 需求范围边界（做什么、明确不做什么）
- 权限归属（谁能做）
- 关键校验规则的具体取值
- 验收标准

其余可以记录为"待确认"，在规格里标 `TODO(待确认)`。

## 提问模板

一次问一批，每条给一个具体场景，别问开放式的"你想要什么"：

```
1. 谁可以使用这个功能？（普通用户 / 管理员 / 两者）
2. 管理员操作后，普通用户应该看到什么？
3. 提交时如果同一时段已被预约，期望是"拒绝"还是"覆盖"？
4. 这条记录创建后可以修改吗？已完成的还能改吗？
5. "做完了"的判定标准是什么？请给一个能自动验证的例子。
```

## 反模式

| 别做 | 为什么 |
|---|---|
| 一次问 30 个问题 | 对方会乱答 |
| 问"你想要什么功能" | 开放式问题拿不到可验收的答案 |
| 自己替对方做决定 | 猜错了后面全白做 —— **猜也要问** |
| 问完不记录 | 结论丢失，规格又要重新推一遍 |
| 把技术方案问题拿去问业务 | 那是 TL 的事，不是 PO 的事 |

## 产出：澄清纪要

把结论写成结构化的纪要，直接交给 `ba-write-spec` 使用。存到 `{{FEATURES_DIR}}/` 下与规格同名的草稿，或直接作为规格的输入。

```markdown
# 澄清纪要：{需求名称}

- 日期：YYYY-MM-DD
- 原始需求：<原话>

## 已确认

| # | 问题 | 结论 | 依据 |
|---|---|---|---|
| Q1 | 谁能用？ | 管理员与普通用户 | 需求方确认 |

## 待确认（不阻塞）

| # | 问题 | 当前假设 | 待谁确认 |
|---|---|---|---|

## 范围边界

**做**：
- ...

**明确不做**：
- ...

## 验收标准（已达成可测）

1. 给定 …，当 …，则 …
```
