# Dev：开发自测

**自测**验证"代码按 Plan 的设计工作"。它 **不是** QA 测试，不能替代验收 —— 详见项目 `{{AGENTS_FILE}}` §10。

## 执行顺序

由快到慢，**先跑快的**，不要一上来就等 E2E：

```
1. 后端单元测试     →  秒级，先跑
2. 后端集成测试     →  分钟级
3. 前端类型/构建    →  秒级
4. 前端单元测试     →  秒级
5. E2E 自测         →  最慢，最后跑
```

## 失败处理

### 先分类，再动手

| 症状 | 多半是 | 动作 |
|---|---|---|
| 断言失败，但代码逻辑看着对 | **实现错了**，不是测试错了 | 改实现 |
| 断言失败，值差一点点 | 边界没考虑到 | 补实现 + 补边界用例 |
| 测试报空指针 / NPE | 测试前置数据缺失 | 补测试数据准备 |
| 整类用例一起挂 | 环境问题（DB 没起、端口占用、依赖服务） | 先修环境，别改代码 |
| 用例之间互相影响 | **测试没有隔离** | 修测试隔离（数据清理） |
| 昨天绿今天红 | 时间/顺序依赖 | 加显式等待，去掉硬等待 |

### 绝对不要做的事

- ❌ 为了让测试变绿而 **修改断言去迁就实现**
- ❌ 删掉失败的用例
- ❌ 加 `@Disabled` / `test.skip` 掩盖问题（除非明确记录原因）
- ❌ 改 **QA 用例**（`{{E2E_DIR}}/tests/qa/`）—— 那是 QA 的判定依据
- ❌ 放宽断言（比如把 `toBe` 改成 `toBeTruthy`）来"通过"

如果确实是 Plan 错了：**回到 Plan 步骤**，改 Plan，不要在代码里悄悄按自己的理解实现。

### 硬等待要改掉

```ts
// ❌ 硬等待，CI 上必 flaky
await page.waitForTimeout(3000)

// ✅ 等具体状态
await expect(page.locator('.result')).toBeVisible({ timeout: 10000 })
```

## 覆盖自查

| 项 | 要求 |
|---|---|
| 每个新增/修改的 API | 1 个 Happy Path + 关键失败分支（参数错误 / 权限不足 / 业务冲突） |
| 每个新聚合 | 业务不变量有对应用例 |
| 每个状态流转 | 合法流转 + 非法流转各一条 |
| 前端新组件/composable | 单元测试（Vitest，与源码同目录 `*.test.ts`） |
| DB 变更 | 迁移脚本 + 测试 `schema.sql` 同步 |
