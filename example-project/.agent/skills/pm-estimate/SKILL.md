# PM：工作量估算

估算不靠拍脑袋，靠 **分类 + 基线表 + 调整系数**。

## 方法

```
基线点数 = 按需求分类查表得到
最终点数 = 基线点数 × 复杂度系数 × 风险系数
人日 = 最终点数 × 团队基线人日/点
```

**基线表**见同目录的 [`baseline.md`](baseline.md)。表里的数字是 **起点**，不是真理 ——
每次迭代结束后用 `pm-retro` 校准它。

## 三步

### 第一步：把需求拆成可独立估算的条目

一条需求如果混了多个类型（"加个预约功能，包含列表、详情、取消"），**拆开估**。

拆到每个条目能归入 **一个** 分类为止。拆不动的条目通常说明需求本身没想清楚 —— 先用 `ba-grill-me`。

### 第二步：查基线表

对每个条目：

1. 在 `baseline.md` 找到匹配的分类 → 拿到基线点数
2. 定 **复杂度系数**：简单 0.8 / 标准 1.0 / 复杂 1.4
3. 定 **风险系数**：低 1.0 / 中 1.2 / 高 1.5

判定依据见 `baseline.md` 的"复杂度判定"与"风险判定"。

### 第三步：汇总并给缓冲

```
原始点数 = Σ 各条目最终点数
缓冲    = 原始点数 × 0.2        # 20% 缓冲
迭代点数 = 原始点数 + 缓冲
```

缓冲不是用来藏估不准的，是用来装 **没预见到的事**（联调、环境问题、需求小改）。

## 输出格式

```markdown
# 估算：{需求名称}

- 日期：YYYY-MM-DD
- 迭代：{迭代名}
- 参与估算：{角色}

## 拆解与估算

| # | 条目 | 分类 | 基线点数 | 复杂度 | 风险 | 最终点数 | 说明 |
|---|---|---|---:|---:|---:|---:|---|
| 1 | 预约列表页 | 列表查询型 | 3 | 标准 1.0 | 低 1.0 | 3.0 | 复用现有表格 |
| 2 | 取消预约 | 状态流转型 | 5 | 复杂 1.4 | 中 1.2 | 8.4 | 含并发冲突处理 |
| 3 | 取消确认弹窗 | 展示型 | 1 | 简单 0.8 | 低 1.0 | 0.8 | 用现成 Modal |

## 汇总

- 原始点数：12.2
- 缓冲（20%）：2.4
- **迭代点数：14.6**

## 团队基线

- 团队基线人日/点：0.5
- **预估人日：7.3 人日**

## 假设与风险

- 假设：复用现有 Modal 与表格组件
- 风险：取消预约的并发冲突处理可能超期（已在复杂度系数中体现）
- 若假设不成立：+2 人日

## 未计入

- QA 用例编写与验收（见 `qa-write-cases`）
- 文档同步（见 `ba-gen-facts`）
- 发布准备（见 `dev-release-plan`）
```

## 校准（重要）

估算不准是常态，但 **不准要知道原因**：

- 估完记下 **实际耗时**，下次迭代开始前对比
- 某类需求连续两次偏差 > 30% → 基线表的点数该改了
- 改基线表时说明原因，别默默调数字

基线表在 `../` 的套件源码里（`agile-team-sdd/skills/pm-estimate-template/baseline.md`），
改完重新 `install.sh --force --skill pm-estimate` 下发到各项目。

## 反模式

| 别做 | 为什么 |
|---|---|
| 按人天直接拍 | 没有基线，无法校准，越估越飘 |
| 一条需求一个数 | 大需求会掩盖小任务的复杂度差异 |
| 不加缓冲 | 第一个意外就爆 |
| 估完了不记录实际值 | 下次还是估不准 |
| 把 QA、文档、发布的时间忘掉 | 这部分一定会占时间 |
