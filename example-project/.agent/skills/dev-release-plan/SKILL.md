# Dev：上线准备清单

把"能不能发"从口头感觉，变成 **一张逐项打勾的清单**。

## 输出位置

`docs/releases/{version}.md`（如 `docs/releases/v1.2.0.md`）

版本号用 `vX.Y.Z`；发版前先建文件，随检查推进逐项打勾。

## 第一步：确定范围

```bash
git log --oneline main..HEAD
git diff main...HEAD --stat
```

列出本次要发的所有变更，并归类：

| 类别 | 影响 | 需要谁确认 |
|---|---|---|
| 新功能 | 无兼容问题 | QA |
| 缺陷修复 | — | QA |
| DB 变更 | **有风险** | TL + DBA |
| 接口变更 | 下游可能受影响 | TL |
| 配置/开关变更 | 行为变化 | TL |
| 依赖升级 | 可能引入回归 | 全员 |

**只要有 DB 变更或接口不兼容变更，这一项就必须单独列出来并写回滚方案。**

## 关键检查点

### DB 变更必须单独评估

```bash
ls ./**/db/migration/*.sql   # 确认脚本清单
```

每个脚本问：

- 加字段有默认值吗？大表加字段要多久？
- 加索引会锁表吗？在生产数据量下要多久？
- 删字段/删表 —— **不可逆**，必须有回滚方案
- 数据订正脚本幂等吗？重跑会不会出事？

### 发布后 30 分钟是黄金窗口

发布后立刻看：

- 健康检查
- **冒烟用例**（`docs/test-cases/smoking-cases/`）
- 错误日志（不是只看进程活着）

发现异常 **立即回滚**，不要"再观察观察"。

## 输出

填好的 `docs/releases/{version}.md` + 一句话结论：

```
上线准备：v1.2.0 —— 8/8 项通过，无 DB 变更，可发布
```

有未完成项时，明确说清 **哪几项未完成、卡在谁那里**。
不要用"基本没问题"这种话。
