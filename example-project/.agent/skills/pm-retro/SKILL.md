# PM：复盘并改进 harness

复盘的产出 **不是** "大家要更认真"，而是 **对 harness 的具体修改**。
harness 指：技能模板、规范文档、目录结构、模板文件、脚本。

## 核心原则

> **人一次不会变，harness 会变。**
> 复盘发现的问题，如果靠"下次注意"解决，就是没解决 —— 必须落到 harness 的某个文件上。

## 第一步：收集事实

复盘前先把这些材料拉齐（不要凭印象）：

```bash
git log --oneline main..HEAD
git log --format="%h %s" --since="2 weeks ago"
```

- 本迭代实际提交的 MR/PR 列表与它们的返工次数
- 跳过步骤的记录（哪些步骤被绕过、为什么）
- 反复出现的问题（同一类错误出现几次）
- 估算偏差（用 `pm-estimate` 的记录对比实际）
- `docs/` 同步检查被勾掉的次数（勾了但没真同步的）

**重点找"重复发生"的事。** 一次是偶发，两次以上就是 harness 的问题。

## 第二步：分类问题

| 类别 | 含义 | 归属 |
|---|---|---|
| **流程缺失** | 少了某一步，或某步没有明确产物 | 加 skill 步骤 / 加检查清单 |
| **规范缺失** | 规则没写，或写了但不好查 | 改 `AGENTS.md` / `docs/standards/` |
| **模板缺失** | 每次都要从头写的东西 | 加模板文件 |
| **Skill 缺失** | 需要一个反复出现的动作，没有对应 skill | 加 skill |
| **Skill 不好用** | 有 skill，但步骤不清楚 / 输出不对口 | 改 skill 模板 |
| **工具缺失** | 需要脚本能自动做的事 | 加脚本 |
| **认知偏差** | 大家理解不一致 | 写进规范 + 培训，不是改工具 |

**"认知偏差" 是唯一不能靠改 harness 解决的** —— 但也要落到"写进规范哪一节"。

## 第三步：产出改进项

每条改进项必须有：**问题证据 + 改哪个文件 + 改成什么**。

```markdown
### 改进项 1：Plan 缺少"接口不兼容变更"检查

- 证据：迭代中 2 次接口变更没同步 `docs/designs/api.yaml`，QA 验收时才发现
- 归类：流程缺失
- 改哪里：`../agile-team-sdd/skills/dev-plan-template/SKILL.md` §规则
- 改成什么：加一条 —— "若新增/修改/删除接口，在 Plan 的'修改清单 → 接口变更'表中必须逐条列出，并在'实施后需更新的 design 文档'中写明 `docs/designs/api.yaml`"
- 谁改：TL
- 怎么验证：下个迭代 Plan 评审时检查这条是否被填
```

**"改哪里"必须指向真实存在的文件路径。** 说不清改哪个文件的改进项，等于没结论。

## 第四步：回写 harness

改进项确认后：

1. 改 **套件源码**：`../agile-team-sdd/skills/<skill>-template/SKILL.md` 等
2. 同步改 **已安装副本**：目标项目的 `.agent/skills/<skill>/SKILL.md`
3. 改动要 **重新下发** 才生效：

```bash
./agile-team-sdd/install.sh <目标项目> --skill <skill> --force
```

只改已安装副本 = 下次重装会丢；只改套件源码 = 本次不生效。**两边都要改。**

## 第五步：验证改进有效

改进项要 **可观测**：

| 改进项 | 怎么验证 |
|---|---|
| 加了检查清单 | 下个迭代评审时该清单被打勾 |
| 加了模板 | 下个迭代该模板被使用（不是被手写替代） |
| 改了 skill | 下个迭代该步骤耗时下降 / 不再被跳过 |
| 加了脚本 | 脚本被执行过，产出被使用 |

**验证不了就说明改进项没落地**，要么改法不对，要么问题判断错了。

## 复盘记录模板

```markdown
# 复盘：{迭代名}

- 日期：YYYY-MM-DD
- 参与角色：{列出}
- 数据来源：{提交记录 / 跳过步骤记录 / 估算对比}

## 事实

- 交付需求：N 条
- 估算点数：X（实际 Y，偏差 Z%）
- 返工 MR：N 个
- 被跳过的步骤：{步骤名 → 次数}
- 重复发生的问题：

| 问题 | 次数 | 影响 |
|---|---:|---|

## 做得好（保留）

- {流程/规范/工具} —— {为什么有效}

## 做得不好（改进项）

见下方改进项表。

## 改进项

| # | 问题证据 | 归类 | 改哪里 | 改成什么 | 谁改 | 怎么验证 | 状态 |
|---|---|---|---|---|---|---|---|

## 下次迭代要盯的 3 件事

1.
2.
3.
```

## 反模式

| 别做 | 为什么 |
|---|---|
| "大家要更仔细" | 不是改进项，无法验证 |
| 只写不改 | 复盘记录不产生价值 |
| 改了不验证 | 改进没落地，下次照旧 |
| 一次改 20 项 | 改不完，最后一项都没生效。**一次改 3 项以内** |
| 改进项没有"改哪里" | 无法执行 |
| 改完不重新下发 | 项目里还是旧版本 |

## 与其他 skill 的关系

- `pm-estimate` —— 复盘时用它的记录校准基线表
- `pm-retro` 产出的改进项如果涉及用例体系 → `qa-write-cases`
- 涉及规范 → 改 `AGENTS.md` / `docs/standards/`
- 涉及新动作 → 在 `../agile-team-sdd/skills/` 加 skill 模板，并更新 `catalog.json`
