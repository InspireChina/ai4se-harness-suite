# BA：编写需求规格

把澄清好的需求落成 **可验收、可实现、可测试** 的规格文档。

## 前置

- 需求已经过 `ba-grill-me` 澄清，阻塞项都有结论
- 已读过 `docs/features/_template/spec.md`（规格模板）与 `AGENTS.md`
- 已查过 `docs/facts/` 下的事实文档，避免和现状冲突
- 已读过项目级术语表 `docs/features/glossary.md`

## 输出位置

`docs/features/<迭代>/<CODE>-<slug>/spec.md`

- 文件夹名用 **JIRA 风格大写编码** + slug（如 `ACC-account`、`BKG-booking`）
- 规格文件固定为目录内的 `spec.md`
- 从 `docs/features/_template/spec.md` 复制起步；同目录可放 `plan.md` / `plan-{slug}.md`
- 一个能力一个文件夹，不要把多个模块塞进一份 spec
- 更新已有模块时基于当前 `spec.md` 改，写明基线版本与目标版本
- **术语表不按 feature 拆分**：新增/变更术语写入项目级 `docs/features/glossary.md`

## 各章节怎么写

### §1 需求说明

- 背景：为什么要做（业务动机，不是技术动机）
- 目标：做完之后什么变了
- 范围：**明确写出"不做什么"** —— 这一节最容易被跳过，也最容易吵架

### 项目术语表 `docs/features/glossary.md`

全项目一份，表头固定：

| 中文 | 英文 | 说明（可选） |
|---|---|---|
| 备注 | remark | |

- 从本 feature 的 §2.3 业务对象、§5 字段表、角色/状态提炼术语，**追加或更新**到项目术语表（去重，不另建 feature 目录下的 glossary）
- 英文用简洁业务词（如 `Account`、`BookingOrder`），不强制代码标识
- `spec.md` §2 附近引用项目术语表（相对路径指向 `docs/features/glossary.md`，例如 feature 目录下写「术语表见」+ 链到 `../../glossary.md`）
- 本轮无新增术语时不必改术语表，但仍须在 spec 中保留引用

### §2~3 功能与权限

- 适用用户表列出角色与场景
- 权限矩阵用 ✅/❌ 逐格填写，不要留空
- 补一条通用规则：**未提及的操作一律不允许**

### §4 业务流程

主流程按步骤写；异常流程单独列：

| 编号 | 触发条件 | 系统行为 | 结果 |
|---|---|---|---|
| EX-001 | 条件 | 行为 | 结果 |

### §5 字段表

这是规格里最容易被写错的部分：

| 字段 | 类型 | 必填 | 描述 | 取值/枚举/来源 | 创建时必填 | 可修改 |
|---|---|---:|---|---|---:|---:|

- **枚举字段要在"取值"列直接写全枚举值和中文含义**，不要写"见字典"
- 「字段」列用中文业务名；类型仍可用英文类型记号（string / enum / datetime 等）
- "创建时必填"与"必填"不同：更新时可能允许留空

### §7 业务规则

**每条规则必须有编号**，格式：

```
R-CREATE-001：必填字段校验
- 适用场景：CREATE
- 条件：…
- 动作：…
```

规则要按场景分组（COMMON / CREATE / QUERY / UPDATE / DELETE），每组都要覆盖：

- 权限校验
- 字段校验（必填、唯一、格式）
- 状态/终态校验
- 审计信息记录
- 引用约束（被引用的数据不能删）

编号是 QA 用例和代码注释的锚点 —— 没有编号的规则在实现阶段一定会走样。

### §9 状态流转

| 当前状态 | 触发动作 | 目标状态 | 允许角色 | 规则编号 |
|---|---|---|---|---|

必须写清 **非法流转** 的处理（拒绝 + 错误码）。

### §12 验收标准

用 Given-When-Then，一条一个编号（`AC-xxx`）：

```
AC-001：正常创建
- 给定：用户具备创建权限
- 当：用户输入合法字段并提交
- 则：系统创建成功，并返回创建后的数据
```

三类都要写：功能验收、数据验收、权限验收。

### §14 原型引用

写清原型路径/链接，并声明冲突时以本规格为准。

## 自检清单

- [ ] `spec.md` 已引用项目术语表；本轮新术语已写入 `docs/features/glossary.md`（中英对照）
- [ ] 每条规则有编号、适用场景、条件、动作
- [ ] 每条验收标准有编号，且可测
- [ ] 字段表里枚举值写全
- [ ] 权限矩阵无空格，"未提及即不允许"已写明
- [ ] 状态流转表完整，含非法流转处理
- [ ] 范围里写了"明确不做什么"
- [ ] NEW / UPDATE 标注正确，UPDATE 有基线版本
- [ ] 没有出现表名、类名、SQL（那是技术方案，不是规格）
- [ ] 没有根据原型 UI 反推业务规则

## 交付后

1. 交给 QA 用 `qa-write-cases` 把验收标准与业务规则转成 `TC-xxx` 用例
2. 交给 TL / 开发用 `dev-plan` 写技术方案
