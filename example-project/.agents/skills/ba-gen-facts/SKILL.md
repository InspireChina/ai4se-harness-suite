# BA：生成事实文档

**事实文档**（`docs/facts/`）描述系统 **当前的真实状态**，不是计划、不是意图。
它的唯一判据是：**和代码对得上吗？**

## 与过程文档的区别

| | 过程文档 | 事实文档 |
|---|---|---|
| 位置 | `docs/features/`（含 `spec.md` / `plan*.md`） | `docs/facts/` |
| 描述 | 需求与方案（会变） | 系统现状（跟着代码变） |
| 变更时机 | 迭代推进时 | **代码一变就变** |
| 写法 | 可以写"待定" | **不许写"待定"** |

## 每份文档的事实来源

**不要凭记忆写，去读源头。**

| 文档 | 事实来源（按可信度排序） |
|---|---|
| `docs/facts/api.yaml` | Controller 的路由与方法签名、DTO 字段、错误码 |
| `docs/facts/db-schema.md` | 迁移脚本 `db/migration/*.sql`、PO 类 |
| `docs/facts/domain-model.md` | 聚合类、值对象、领域服务 |
| `docs/facts/tech-topic/businessrule.md` | `IBusinessRule` 实现类 + 规则配置文件 |
| `docs/facts/tech-topic/data-dict.md` | 枚举类 + 数据字典注册类 |
| `tech-topic/*.md` | 对应模块的实现 |

## 生成流程

```
1. 确定范围        —— 这次变更动了哪些模块？
2. 读源头          —— 从代码/迁移脚本/配置里读出真实状态
3. 逐份对照        —— 现有文档哪里对、哪里不对、哪里缺
4. 改文档          —— 只改与代码不符的部分，不重写风格
5. 反向验证        —— 把文档当输入，逐条核对代码
6. 报告            —— 列出改了哪些文档、每处对应的代码依据
```

## 各文档的检查点

### API

- 路径、方法、请求参数、响应字段、状态码、错误码，与 Controller 逐一对上
- 分页参数、鉴权要求（哪些接口要登录/要管理员）
- 新增接口要标清楚 **用途**，不要只抄签名

### 数据库

- 表名、字段名、类型、是否可空、主键、索引、默认值
- 迁移脚本版本号与内容对应
- 字段含义写中文说明，不要只列结构
- **敏感字段**（密码、手机号）标注存储方式（加密/脱敏）

### 领域模型

- 聚合根、实体、值对象、聚合之间的关系
- 每个聚合的业务不变量（哪些操作非法）
- 状态机：状态集合 + 允许的流转

### 业务规则与数据字典

- 规则：编号、分类、条件、动作，与实现枚举一一对应
- 字典：每个枚举类型的取值、含义、注册位置

## 写法

- 用 **陈述句**："预约状态包含 PENDING / CONFIRMED / COMPLETED / CANCELLED"
- 不要用 "应该"、"计划"、"预计" —— 事实文档里没有将来时
- 有例外就在同处说明，不要分散在多处
- 每个结论都要能指到代码位置（类名 / 文件名），方便复核

## 与需求规格的关系

- 需求规格写的、但 **还没实现** 的，不进事实文档
- 实现里 **多出来** 的行为：要么补进需求规格（并确认），要么改掉 —— 不能只躺在事实文档里
- 两者冲突时，**以需求规格为准**（业务规则），但要修实现

## 输出

改完后在提交描述里写清楚：

```
事实文档同步：
- docs/facts/api.yaml — 新增 GET /api/v1/xxx（依据 XxxController#getXxx）
- docs/facts/db-schema.md — appointments 表新增 remark 字段（依据 V2026xxxx__add_remark.sql）
```

## 自检清单

- [ ] 每条结论都能指到代码/脚本位置
- [ ] 没有"应该"、"计划"、"待补充"
- [ ] 没实现的内容没有写进去
- [ ] 错误码、枚举值与代码完全一致
- [ ] 敏感字段已标注
- [ ] `docs/facts/README.md` 的专题索引已同步
